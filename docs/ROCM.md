# ROCm on aarch64 for gfx906

AMD publishes no aarch64 ROCm packages, so you have to build it.
`scripts/build-rocm-aarch64.sh` builds the minimum llama.cpp needs, at tag
`rocm-6.3.3`, for gfx906 only, into `/opt/rocm`:

| Stage | Source | Provides |
| --- | --- | --- |
| `rocm_cmake` | ROCm/rocm-cmake | CMake helpers |
| `llvm` | ROCm/llvm-project | clang, lld, the AMDGPU backend (`/opt/rocm/llvm`) |
| `device_libs`, `comgr`, `hipcc` | ROCm/llvm-project `amd/*` | device bitcode libraries, code-object manager, hipcc |
| `rocr` | ROCm/ROCR-Runtime | `libhsa-runtime64`, `libhsakmt` (ROCT was merged into ROCR in 6.3) |
| `rocminfo` | ROCm/rocminfo | `rocminfo`, `rocm_agent_enumerator` |
| `hip` | ROCm/clr + ROCm/HIP | `libamdhip64`, HIP headers |
| `hipblas_common`, `rocblas`, `hipblas` | ROCm/* | BLAS for llama.cpp |

No source patches are needed. Every one of these projects is portable C++, and
the GPU code is generated by LLVM's AMDGPU backend regardless of the host
architecture.

## Why 6.3.3

gfx906 entered maintenance in ROCm 6.x, and newer releases trim its rocBLAS
kernels and test coverage. 6.3.3 is the last release where gfx906 is fully
present in every component. If you want to try newer releases, set
`ROCM_VER=6.4.x`; it will probably still build for gfx906.

## Resources

- **Disk:** about 60 GB for sources and build trees. Put `SRC` on NVMe or USB
  SSD storage, not the SD card.
- **RAM:** LLVM linking is the peak. On a 16 GB board use `JOBS=6 LINK_JOBS=1`
  and add 8–16 GB of swap. On 8 GB, use `JOBS=3` plus swap, or build on a
  bigger aarch64 machine (a cloud Graviton or Ampere instance works) and copy
  `/opt/rocm` over as a tarball.
- **Time:** expect several hours on RK3588. LLVM and rocBLAS/Tensile take
  most of it.

To resume after a failure, fix the problem and rerun from the failed stage:
`./scripts/build-rocm-aarch64.sh rocblas`.

## Verify

```bash
. scripts/rocm-env.sh
rocminfo | grep -E 'Name:.*gfx906|Marketing'
cat > /tmp/t.hip <<'EOF'
#include <hip/hip_runtime.h>
#include <cstdio>
__global__ void k(int *p){ p[threadIdx.x] = threadIdx.x * 2; }
int main(){ int *d,h[64]; hipMalloc(&d,256); k<<<1,64>>>(d);
  hipMemcpy(h,d,256,hipMemcpyDeviceToHost); printf("%d %d\n",h[1],h[63]); }
EOF
hipcc --offload-arch=gfx906 /tmp/t.hip -o /tmp/t && /tmp/t     # prints: 2 126
```

## Troubleshooting

| Symptom | Try |
| --- | --- |
| `rocminfo`: `HSA_STATUS_ERROR_OUT_OF_RESOURCES` or no GPU agent | `/dev/kfd` is missing, or your user isn't in the `render` and `video` groups |
| `hipMemcpy` hangs or returns wrong data | `HSA_ENABLE_SDMA=0` (uses shader copies instead of the SDMA engines); then look at the coherency section in [KERNEL.md](KERNEL.md) |
| rocBLAS: `Cannot read TensileLibrary.dat ... for GPU arch : gfx906` | rocBLAS was built without gfx906. Rerun the `rocblas` stage, and check `AMDGPU_TARGETS` |
| Tensile stage runs out of memory | Lower `JOBS` (it's passed as `Tensile_CPU_THREADS`) |
| HIP kernels fault right after launch (`Memory access fault by GPU`) | Run with `AMD_LOG_LEVEL=3` and capture `dmesg`. This is usually coherency or the BAR, not ROCm |

## llama.cpp tips for the MI50

- Fully offload with `-ngl 99`. Partial offload over Gen3 x4 is slow.
- On recent llama.cpp builds, `-fa on` (flash attention) works on gfx906 with
  both the HIP and Vulkan backends and saves VRAM at long context lengths.
- Compare the backends with `llama-bench`. On gfx906, Vulkan often matches
  HIP for token generation, while HIP is usually faster at prompt processing.
